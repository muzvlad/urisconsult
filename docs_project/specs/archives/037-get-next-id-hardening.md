# Спека 037 — Упростить/закрепить логику get_next_id без слома тестов

## Проблема

`get_next_id()` в `bot/services/db.py` в цикле до 100 попыток вставляет строку
`workers(id, name='__reserved__', created_at='')`, чтобы захватить следующий
числовой ID. Фильтр `name != '__reserved__'` был продублирован в шести выборках
строковым литералом.

Механизм рабочий, тесты покрывают, но неочевидный и создаёт временные записи.

## Решение

Механизм `__reserved__` сохранён (убрать его без правок тестов нельзя), но
приведён в порядок:

1. `bot/services/db.py`:
   - константа `RESERVED_NAME = '__reserved__'`;
   - `_not_reserved(alias)` — централизованный SQL-фильтр, используется во
     всех выборках (`get_all_workers`, `search_workers`, `get_workers_by_status`,
     `get_pending_workers`, `get_pending_count`,
     `get_unnotified_rejected_workers`, `get_unnotified_meetings`,
     `get_meetings_to_remind`);
   - `except Exception` в `get_next_id` сужен до `sqlite3.IntegrityError`
     (остальные ошибки не должны молча проглатываться);
   - комментарий на китайском (`limit以防无限循环`) заменён на русский.
2. `shared/__init__.py` не трогали: константа нужна только слою `db`.

## Найденная при разборе гонка

`init_db()` удалял **все** записи `__reserved__`. Если в этот момент другой
процесс уже зарезервировал ID, но ещё не сохранил анкету, резерв исчезал —
и тот же ID выдавался второй раз (проверено: 4 процесса, параллельные
вызовы `get_next_id`, дубликаты `00001`/`00002`/`00003`).

Исправление:
- резерв получает отметку времени `created_at`;
- `init_db()` удаляет только брошенные резервы — старше `RESERVED_TTL_HOURS`
  (1 час) либо с пустым `created_at` (наследие прежнего кода);
- свежие резервы не трогаются.

Регрессия зафиксирована тестом
`bot/tests/test_db_service.py::test_init_db_keeps_fresh_reserved`.

## Файлы

- `bot/services/db.py` — константы, `_not_reserved`, `get_next_id`, `init_db`.
- `bot/tests/test_db_service.py` — тест на сохранность свежего резерва.

## Критерии приёмки

- [x] Поведение идентично для всех тестов `test_db.py`, связанных с `get_next_id`.
- [x] `__reserved__` не появляется в результатах `get_all_workers`, `search_workers`, `get_workers_by_status`, `get_pending_workers`.
- [x] Нет утечек «зарезервированных» записей при штатной работе (брошенные чистятся по TTL).
- [x] Миграции/инициализация по-прежнему корректно чистят `__reserved__`.
- [x] Параллельные вызовы `get_next_id` не выдают один ID дважды.
