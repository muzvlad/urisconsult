# Спека 039 — Модель доступа к БД при разделённых бот+UI (разные машины), единая SQLite БД

## Контекст

В проде бот и UI запущены на **разных** машинах и работают с **одной** SQLite
базой (сетевой ресурс). UI общается с ботом через HTTP API
(`UI/src/api_client.py` → `bot/api_server.py`) — это правильное решение, его
сохраняем.

## Проблема

SQLite на сетевом шаре чувствителен к блокировкам. Одновременная запись с
разных машин даёт `database is locked`. Длинные транзакции ухудшают ситуацию.

## Решение

### Архитектурное

- **Жёстко зафиксировано**: только `bot/services/db.py` работает с SQLite.
  Проверено: в `UI/src/**` нет ни `import sqlite3`, ни `import aiosqlite`, ни
  прямого открытия БД; `db_path` в `UI/src/config.py` используется только для
  диагностического лога.
- Удалён мёртвый код, из-за которого UI тянул `sqlite3`:
  `Worker.from_row`, `WorkerDocument`, `WorkerMeeting` — UI строит модели из
  ответов API (`api_client._dict_to_worker`). Убран и `--hidden-import=sqlite3`
  в `UI/build_exe.py`.
- `bot/api_server.py` прямого доступа к SQLite не имеет.

### Практика работы с SQLite

- `PRAGMA busy_timeout=30000` и `PRAGMA foreign_keys=ON` — на каждом
  соединении, без блокировок.
- `PRAGMA journal_mode=WAL` — **один раз на файл БД** (режим хранится в
  заголовке файла), а не на каждом подключении. Причина: смена режима журнала
  требует эксклюзивной блокировки и при конкуренции возвращает `SQLITE_BUSY`,
  **не вызывая busy-handler**, — на практике это давало
  `database is locked` при каждом обращении к БД.
- `init_db()` выполняется в транзакции `BEGIN IMMEDIATE` — инициализация
  сериализована между процессами, при сбое изменения откатываются целиком.
- Транзакции короткие: commit сразу после пачки логически связных изменений,
  соединение не держится во время сетевых вызовов и тяжёлых вычислений.

### Найденные и исправленные блокировки

Проверка четырьмя параллельными процессами на одной БД выявила три дефекта:

1. `PRAGMA journal_mode=WAL` выполнялся на **каждом** подключении и без
   `busy_timeout` падал с `database is locked` (исправлено — см. выше).
2. `init_db()` не был сериализован: бот и API, стартующие одновременно, выполняли
   миграции параллельно (исправлено через `BEGIN IMMEDIATE`).
3. `get_next_id()` читал максимум через `fetchone()` — незакрытый курсор
   оставлял read-lock, и следующий `INSERT` шёл как upgrade read→write, что
   SQLite отклоняет **без** повтора. Курсор теперь исчерпывается через
   `fetchall()`.

После правок: 4 процесса × 20 итераций — без `database is locked`, без
дубликатов ID, время прогона 90 с → 1.3 с.

## Инфраструктурные замечания

- SQLite работает по сети, но надёжнее всего при **одном писателе**. Текущая
  схема (писатель — бот/API) это требование соблюдает, нарушать нельзя.
- **WAL на сетевом ресурсе требует поддержки POSIX advisory locks.** На SMB-шере
  WAL может не работать (нужны `-wal`/`-shm` файлы и блокировки). Если БД
  лежит на SMB и появляются `disk I/O error` — переключать БД в rollback-режим;
  это решение уровня развёртывания, а не кода.
- Бот должен стартовать раньше API: схему и WAL создаёт бот (`init_db`),
  API-сервер только обращается к готовой БД.

## Файлы

- `bot/services/db.py` — PRAGMA, `init_db`, `_ensure_wal`, `get_next_id`,
  короткие транзакции, комментарии о сетевом ресурсе.
- `UI/src/models.py` — удалён мёртвый код с `sqlite3`.
- `UI/build_exe.py` — убран `--hidden-import=sqlite3`.

## Критерии приёмки

- [x] В UI-коде нет импортов `aiosqlite`/`sqlite3`, нет прямого открытия БД.
- [x] Весь write-путь UI идёт через HTTP API.
- [x] В `bot/services/db.py` транзакции короткие, нет висящих соединений.
- [x] `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout`, `PRAGMA foreign_keys=ON` настроены.
- [x] Комментарии в `db.py` о сетевом ресурсе и коротких транзакциях добавлены.
- [x] Проверка: при одновременных действиях UI + фоновых задач бота массовых
      «database is locked» нет (проверено параллельными процессами).
